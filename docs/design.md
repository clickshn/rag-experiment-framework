# rag-experiment-framework 설계 문서 (초안)

Nov 17, 2026 · 석한나

## 1. 목표와 범위

RAG를 구축할 때 들어가는 부품(생성 모델, 청킹, 임베딩, 벡터DB, 검색 전략, 리랭크, 생성 전략, 판정 모델)을 바꿔 끼우며, **다시 만들 수 있고 공정하게** 비교하는 공개 프레임워크다. 평가 문항을 만드는 과정과 사람 검토를 대시보드에서 할 수 있게 한다.

**대시보드에서 부품을 골라 조합하고 바로 평가·검증한다.** 사용자는 화면에서 청킹·임베딩·벡터DB·검색·리랭크·생성·판정 부품을 고르고 설정을 채워 구성을 만든 뒤, 문항 세트와 평가 수준을 정해 실행하고, 진행·결과·비교·사람 검토까지 한 화면에서 한다. YAML과 CLI는 같은 일을 코드로 하는 길이고, 화면에서 만든 구성도 YAML로 저장돼 같은 버전 해시를 갖는다. 그래서 화면으로 돌린 실험도 다시 만들 수 있다.

출발점은 DASP 2.0 P0의 평가 경험이다. 코드는 처음부터 새로 짜고, P0에서 검증한 평가 원칙(버전 해시, 동결, 봉인, 블라인드 검토)을 기본 동작으로 넣는다.

### 누가 쓰나

RAG를 구축하면서 "무엇을 고를까"를 숫자로 정해야 하는 사람이다. 부품 하나가 아니라 RAG를 이루는 모든 선택이 대상이다.

| 상황 | 답하려는 질문 |
| --- | --- |
| **생성 모델 선택** | 폐쇄망에서 쓸 로컬 모델 중 어느 것이 상용 수준에 가장 가까운가, 상용 모델 중 가격 대비 무엇이 나은가, 우리 GPU에 올라가는가 |
| **청킹·임베딩·벡터DB 선택** | 우리 문서는 어떻게 나눠야 하나, 한국어에 맞는 임베딩은 무엇인가, 벡터DB를 바꿔도 결과가 같은가 |
| **검색·리랭크 설계** | 벡터만으로 충분한가, 키워드를 섞어야 하나, 근거는 몇 개가 적당한가 |
| **생성 전략** | 프롬프트·출력 형식·도구 호출 방식 중 무엇이 나은가 |
| **평가 체계 만들기** | 평가 문항을 어떻게 만들고 검수하나, 판정 모델을 믿어도 되나, 사람 검토는 어디에 써야 하나 |
| **검증·도입 판단** | 미리 정한 기준을 넘는가(P0 같은 검증), 도입해도 되는가 |
| **변경 후 회귀 확인** | 모델·검색·프롬프트를 바꾼 뒤 품질이 떨어지지 않았는가 |
| **원인 진단** | 틀린 답은 어디서 생겼나(청킹·검색·리랭크·생성) |

특히 상용 API를 쓸 수 없는 폐쇄망·공공기관 환경에서 로컬 모델과 로컬 검색 부품만으로 충분한지 검증해야 하는 팀이 주된 사용자다.

### 범위

| 넣음 | 내용 |
| --- | --- |
| 비교 대상 | 생성 모델, 청킹 전략, 임베딩 모델, 벡터DB, 검색 전략, 리랭킹, 생성 전략(프롬프트 등), 판정 모델 |
| 데이터 | 법령(국가법령정보센터 Open API)을 첫 예제로, 다른 문서 말뭉치도 같은 인터페이스로 |
| 문항 | 생성·검사·사람 검토·동결까지 프레임워크가 지원 |
| 채점 | 코드 규칙, LLM 판정(여러 개 교차), 사람 채점 |
| 화면 | 문항 검토, 실험 목록·비교, 문항 상세, 답 채점, 게이트 |

### 비목표

- 서비스용 RAG 엔진이 아니다. 실험에 필요한 만큼만 파이프라인을 돌린다(인증·권한·스트리밍 없음).
- **모델을 직접 띄우지 않는다.** 모델 가중치를 받아 GPU에 올리고 서버로 띄우는 일(서빙)은 사용자가 vLLM·Ollama 같은 도구로 따로 하고, 프레임워크는 그 서버의 주소(OpenAI 호환 API)를 받아 부르기만 한다. 상용 API도 같은 방식으로 주소·키만 넣으면 된다. P0에서 서버 스크립트(up.sh)가 vLLM을 띄우고 평가 하네스는 주소로 불렀던 것과 같은 나눔이다.
- 학습·파인튜닝은 다루지 않는다.
- 다중 사용자 협업·권한 관리는 처음에는 넣지 않는다(한 사람이 로컬에서 쓰는 것 기준).

## 2. 설계 원칙

P0에서 검증한 것과 P0에서 실제로 문제가 됐던 것을 기본 동작으로 넣는다. 사용자가 따로 켜지 않아도 지켜지게 하는 것이 핵심이다.

| 원칙 | 무엇을 막나 | P0에서의 근거 |
| --- | --- | --- |
| **구성·채점을 해시로 버전화** | 조건이 다른 실행끼리 비교하는 일 | 구성·채점 버전이 같아야 dev와 test를 같은 조건으로 인정했음 |
| **검색 평가와 생성 평가 분리** | 검색 비교에 비싼 생성까지 돌리는 일 | P0 불합격 원인을 '정답 조문이 근거에 모두 들었나'만으로 가름 |
| **문항 단위 지표** | 조문 단위 recall이 실제 성능을 가리는 일 | recall@5는 16%p 하락, 정답률은 50%p 하락 |
| **dev / val / test 분리, test 봉인** | test에 맞춘 조정 | dev 반복 조정으로 dev 값이 부풀려짐, test 노출 뒤 재사용 불가 |
| **합격선 동결과 코드 판정** | 결과를 보고 기준을 바꾸는 일 | 합격선을 해시에 넣고 코드가 결론을 냄 |
| **기준표와 코드 조건 대조** | 정한 기준이 코드에서 빠지는 일 | ADR 16개 조건 중 14개만 코드에 들어감 |
| **판정 점검과 교차 판정** | 판정 모델이 바뀌거나 한쪽으로 치우치는 일 | 점검 문항으로 상태 확인, test 표본 일치율 85.4% |
| **블라인드 사람 검토** | 구성을 알고 채점해 판단이 흔들리는 일 | A·B와 판정 결과를 가린 채점 페이지 |
| **must 기준 해석 갈림 점검** | 문항 기준이 애매해 채점이 갈리는 일 | test 어긋남 7건이 모두 특정 문항에 몰림 |
| **실행 기록을 파일로, 다시 계산 가능** | DB가 사라지면 결과도 사라지는 일 | runs/ 내보내기와 restore-check |

### 구현 원칙

- **부품은 인터페이스로**: 새 부품은 인터페이스를 구현해 등록만 하면 구성 파일에서 고를 수 있다. 프레임워크 본체를 고치지 않는다.
- **설정은 YAML, 동작은 코드**: 실험 조건은 모두 YAML에 있고, YAML만 보면 어떤 조건으로 돌았는지 안다.
- **처음엔 가볍게**: SQLite와 파일로 시작하고, 필요할 때 바꾼다. 사용자는 `pip install rag-experiment-framework`(또는 `uv add`)와 API 주소만으로 쓸 수 있어야 한다. 개발은 uv로 한다. PyPI 배포 시점은 R0 이후에 정한다.
- **비밀값은 환경 변수로만**: API 키·법령 API 인증키는 레포·실행 기록·대시보드 어디에도 남지 않는다.

## 3. 전체 구조

프레임워크는 세 단계로 이뤄진다. 데이터 준비에서 말뭉치와 문항을 만들어 얼리고, 실험 실행에서 부품을 조합해 돌리고, 채점·기록에서 점수를 내고 남긴다. 대시보드는 세 단계를 모두 화면으로 보여 주고, 사람이 개입하는 두 곳(문항 검토, 답 채점)을 맡는다.

```text
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  데이터 준비  │ →  │  실험 실행   │ →  │  채점·기록   │
│ 말뭉치·문항  │    │ 부품 조합    │    │ 점수·실행 기록│
│ 만들어 얼림  │    │ 세 수준 실행 │    │ 보고서       │
└──────┬───────┘    └──────┬───────┘    └──────┬───────┘
       └───────────────────┼───────────────────┘
                    ┌──────┴───────┐
                    │   대시보드   │  세 단계를 모두 보여 줌
                    │ (문항 검토·  │  사람이 개입하는 곳:
                    │  답 채점)    │  문항 검토, 답 채점
                    └──────────────┘
```

- **데이터 준비**는 한 번 얼리면 여러 실험이 같이 쓴다. 문항 세트도 해시로 버전화된다.
- **실험 실행**은 세 수준이다.
  - **검색만**: 청킹·임베딩·벡터DB·검색·리랭크를 비교. 생성 없이 돌아 빠르고 싸다.
  - **생성만(정답 근거 주입)**: 문항의 정답 덩어리를 근거로 직접 넣어 생성 모델·프롬프트만 비교. 검색 실력이 섞이지 않아 모델끼리 공정하게 비교된다. P0에서 근거가 다 든 문항만 따로 본 것을 정식 모드로 만든 것이다.
  - **처음부터 끝까지**: 실제 검색 결과로 생성·채점. 서비스 조건에 가장 가깝다.
- **권장 순서**: 생성만으로 모델 후보를 거르고, 검색만으로 검색 조합을 좁힌 뒤, 남은 조합만 처음부터 끝까지 돌린다. "어떤 모델을 쓸까 → 부족한 곳 찾기 → 원인 진단 → 부품 고치기"가 이 프레임워크가 지원하는 기본 흐름이다.
- **채점·기록**은 코드 규칙 → LLM 판정 → 사람 채점 순서로, 코드로 판단할 수 있는 것은 모델에 맡기지 않는다. 모든 결과는 실행 기록 파일로 남아 다시 계산할 수 있다.

## 4. 부품 인터페이스

부품마다 작은 인터페이스(Python `Protocol`)를 두고, 구현은 이름으로 등록한다. 구성 파일의 `type` 값이 그 이름이다. 부품은 자기 설정을 받아 만들어지고, 자기 버전 정보(모델 이름·revision 등)를 내놓아 구성 해시에 들어간다.

| 부품 | 하는 일 | R0 구현 | 나중에 |
| --- | --- | --- | --- |
| Corpus | 원문 문서를 읽음 | 법령(Open API XML) | 폴더의 텍스트·마크다운(R2), PDF, HWPX |
| Chunker | 문서를 덩어리로 나눔 | 법령 조 단위 | 고정 길이(R2), 문단·의미 단위, 쪽 단위 |
| Embedder | 덩어리·질문을 벡터로 | Protocol만 | OpenAI 호환(vLLM 등, R2), sentence-transformers 직접 로드 |
| VectorStore | 벡터 저장·검색 | Protocol만 | 메모리 안 정확 검색(R2), pgvector, Qdrant, FAISS |
| Retriever | 검색 전략 | 정답 근거 주입(oracle) | 벡터, 번호 정확 일치(질문 속 "제N조"), 둘의 합치기, BM25, 하이브리드(RRF)(이상 R2), 질문 분해, 참조 조문 따라가기 |
| Reranker | 후보 재정렬 | Protocol만 | 없음·OpenAI 호환 rerank(R2), 교차 인코더 직접 로드 |
| Generator | 근거로 답 생성 | OpenAI 호환 chat + 프롬프트 템플릿 | 도구 호출, JSON 강제, 다단계 |
| Judge | 답 채점 | 코드 규칙, LLM(must·fail 배열) | 교차 판정 합치기 |
| QuestionGenerator | 문항 초안 생성 | Protocol만 | LLM·유형별 템플릿(R3), 난이도 조건 제어 |

**모델 메타 정보**: Generator·Embedder·Reranker·Judge는 설정에 모델 선택에 필요한 정보를 함께 적는다. 가격(상용은 입력·출력 토큰 단가, 로컬은 GPU 시간당 비용), 필요한 GPU 메모리, 라이선스, 폐쇄망 반입 가능 여부, 상용 모델 종료 예정일. 이 정보는 구성 해시에 넣지 않고(가격이 바뀌어도 같은 실험), 비교 화면과 비용 계산에만 쓴다.

### 인터페이스 (U1에서 확정)

도메인 타입은 pydantic `BaseModel(frozen=True)`이다. 같은 정의로 바깥 입력(문항 파일 등)을 검증하고, 실행 기록 JSON으로 왕복한다. 모든 부품은 클래스 속성 `version`(필수, 동작이 바뀌면 올림)과 `fingerprint()`를 갖는다. 구현은 `src/ragexp/components/protocols.py`에 있다.

```python
class Embedder(Protocol):
    version: ClassVar[str]
    def embed(self, texts: Sequence[str], *, kind: Literal["query", "document"]) -> list[list[float]]: ...
    def dimension(self) -> int: ...
    def fingerprint(self) -> Fingerprint: ...   # 모델·revision·차원 → 구성 해시에 들어감

class Retriever(Protocol):
    def retrieve(self, query: RetrievalQuery) -> list[Hit]: ...   # k는 설정값

class Generator(Protocol):
    def generate(self, inp: GenerationInput, context: Sequence[Chunk]) -> Answer: ...

class Judge(Protocol):
    def judge(self, question: JudgeQuestion, response: JudgeInput) -> Verdict: ...
```

도메인 타입은 `Document`(+`Section`), `Chunk`, `Hit`, `Question`, `Usage`, `Answer`, `Verdict` 7개다. 설계 원칙 몇 가지는 보조 타입으로 강제한다.

| 원칙 | 타입으로 막는 방법 |
| --- | --- |
| 정답 정보는 oracle 검색만 본다 | 검색 입력 `RetrievalQuery.gold`는 정답 근거가 필요한 검색기(`needs_gold`)에만, 생성만 수준에서만 채운다. 생성 입력 `GenerationInput`에는 gold·must·fail 칸이 없다. |
| 판정은 블라인드 | 판정 입력 `JudgeQuestion`(qid·split·provenance 없음), `JudgeInput`(모델 이름·usage 없음) |
| 정오는 코드가 계산 | 판정 출력 `Verdict`에 정오 칸이 없고, 지표 이름으로도 정오(`correct`·`accuracy` 등)를 낼 수 없다. must·fail 참·거짓만 내고 정오는 채점 코드가 계산한다. |
| 주소를 기록에 남기지 않음 | `Answer.error`·`Answer.warnings`·`Answer.served_model`·`Verdict.note`에 주소(URL·IPv4·호스트:포트)가 있으면 생성 시 오류. `model_copy(update=)`도 다시 검증한다. |

**등록과 외부 부품**: `@register(kind, name)`은 클래스에 표시만 붙이고, 등록은 레지스트리가 한다. 밖에서 만든 부품은 entry point 그룹 `ragexp.components`에 **`<kind>.<name>` 이름**으로 선언한다.

```toml
[project.entry-points."ragexp.components"]
"retriever.hybrid" = "my_pkg.retrievers:HybridRetriever"
```

이름만 보고도 어떤 부품이 있는지 알 수 있어서, 실제로 쓰는 부품만 그때 불러온다. 쓰는 부품을 불러오지 못하면 플러그인 이름을 담아 실행 전에 멈춘다. 쓰지 않는 플러그인의 문제는 경고만 낸다. 내장 부품도 같은 방식으로 등록한다.

**부품이 지킬 약속**(구성 로더가 쓰는 것):

- 생성기는 설정으로 `prompt_template: str`(프롬프트 파일 내용)을 받는다. `ragexp.config.GeneratorSettings`를 상속하면 된다. 렌더링 코드가 바뀌면 생성기 `version`을 올린다.
- 접속 칸(`base_url`, `api_key` …)을 받는 부품은 `config_model`에서 그 칸을 `SecretStr`로 선언한다. 접속 칸은 설정 맨 위에만 둔다.
- 판정 부품은 `judge_kind`(`code`·`model`)를 밝힐 수 있다. 그러면 로더가 판정 역할(`role`)과 맞는지 검사한다(code는 rules만, model은 rules 불가).
- generator·judge 중 `config_model`에 `run` 칸이 있는 부품(`ragexp.config.ModelSettings`를 상속하면 생김)은 로더가 실행 설정 `run`을 `settings.run`으로 넣어 준다. `run`은 해시에 들어가지 않는다. (U3. R2에서 embedder·reranker가 모델을 부르게 되면 그때 넓힌다)
- 모델 클라이언트(`ragexp.client.ChatClient`)는 부품 생성자에서 만들지 않고 **처음 호출할 때** 만든다. 그래서 환경 변수 없이(`config check --no-env`) 부품을 만들고 해시를 낼 수 있다. 자리표시 값이면 클라이언트를 만들 때 오류가 난다. (U3)
- 생성기는 클라이언트가 돌려준 `Answer`(경고·시도 횟수 포함)를 그대로 돌려준다. (U3)
- 출력에 영향을 주는 요청 파라미터는 모두 `settings.params`(fingerprint에 들어감)로만 받는다. 호출할 때 덮어쓰지 않는다. 예외는 `response_format` 하나이고, 문항 데이터(`answer_schema`)에서 나온 값만 넘긴다. (U3)

### 모델 호출 통로

모든 모델 호출(생성·임베딩·리랭크·판정)은 하나의 클라이언트 층을 지난다. 여기서 재시도, 시간 제한, 토큰·지연 기록, 응답의 실제 모델 이름 확인, 잘림(finish\_reason) 구분을 한 곳에서 처리한다. P0의 게이트웨이를 단순화한 것이고, 데이터 등급 통제는 선택 기능으로 둔다(R0에서는 만들지 않음).

**R0 구현(U3)**: `src/ragexp/client.py`의 `ChatClient`가 OpenAI 호환 `/chat/completions`를 httpx로 부른다(임베딩·리랭크 호출은 R2). `base_url`은 `/v1`까지 포함한 주소로 받고, 그 뒤에 `/chat/completions`만 붙인다.

| 항목 | 정한 것 |
| --- | --- |
| 시간 제한 | 응답 기다림은 `run.timeout_s`(기본 180초), 연결은 10초 고정 |
| 프록시 | 모델별 접속 설정 `proxy: none \| env`(기본 none, 해시 밖). none은 환경 변수·시스템 프록시를 읽지 않고 직접 연결하고, env는 그것을 따른다. 상용 A(회사 프록시)와 로컬 B(사내망 직접)를 한 실행에서 비교하므로 실행 전체가 아니라 모델마다 정한다. none에서 연결을 맺지 못하면 오류 문구에 "회사 프록시가 필요하면 이 모델 설정에 proxy: env"를 붙인다 |
| 호출 안 재시도 | 서버 사정 실패만. 전체 `1 + run.max_retries`번(기본 3번), 그중 시간 초과는 최대 2번. 대기는 1초 × 2^(시도−1)(최대 30초)이고, `Retry-After`(초·HTTP 날짜)가 있으면 따르되 60초를 넘지 않는다. 지터 없음 |
| 지연 | `Usage.latency_ms`는 마지막 시도 한 번, `Usage.total_ms`는 재시도·대기를 포함한 전체. 시도 횟수는 `Answer.attempts` |
| 잘림 | `finish_reason=length`는 오류가 아니다. 재시도하지 않고 그대로 기록한다 |
| 모델 이름 | 응답 `model`이 설정과 다르면(대소문자 구분) `Answer.warnings`에 경고한다. 경로형이면 마지막 조각만 기록하고 `--served-model-name` 안내를 붙인다. 주소가 들어 있으면 기록하지 않는다 |
| 새지 않게 | 오류 문구는 고정 문구다. 주소·키·응답 본문을 넣지 않고, 오류일 때 `Answer.text`는 빈 문자열이다. 예외를 바꿔 낼 때 원래 예외를 잇지 않는다(`from None`) |

**실패 분류 셋**(클라이언트가 `failure_class`로 내고, 실행기·채점기가 쓴다):

| 분류 | `error_kind` | 호출 안 재시도 | 실행에서 |
| --- | --- | --- | --- |
| 서버 사정 | `connect`(네트워크 오류·연결 끊김), `timeout`, `http_status`(408·429·5xx), `other`(그 밖의 httpx 오류·모르는 상태 코드) | 함 | 실행 단위로 한 번 다시 돌리고, 남은 비율로 실행 무효를 판단한다(§7.1) |
| 모델·문항 사정 | `client_error`(그 밖의 4xx), `parse`(응답 형식 오류), 잘림(`finish_reason=length`) | 안 함 | 항목 실패로 채점하고 건수를 따로 표시한다 |
| 설정 오류 | `config_error`(401·403·404) | 안 함 | 실행을 바로 멈춘다. 칸 경로와 원인만 안내하고 값은 넣지 않는다 |

`other`를 서버 사정에 두는 것은 모르는 오류가 조용히 오답으로 채점되지 않게 하려는 것이다.

## 5. 구성 파일과 버전

실험 조건은 YAML 하나에 모두 적는다. 실행하면 각 부품의 fingerprint와 공통 값(level, 프롬프트 내용 해시 등)으로 arm별 구성 버전과 나머지 해시를 만들고, 원재료와 함께 실행 기록에 남긴다(아래 표).

```yaml
# experiments/law_hybrid.yaml (예시)
name: law-hybrid-v1
corpus:   {type: law_api, snapshot: data/snapshots/law-2026-11-17}
chunker:  {type: law_article}
embedder: {type: openai_compat, base_url: ${EMBED_URL}, model: nlpai-lab/KURE-v1}
vector_store: {type: memory_exact, distance: cosine}
retriever: {type: hybrid, vector_k: 20, bm25_k: 20, fusion: rrf}
reranker:  {type: openai_compat_rerank, model: dragonkue/bge-reranker-v2-m3-ko, top_n: 5}
generators:            # 비교할 구성(A·B …)
  A:
    type: openai_compat
    base_url: ${OPENAI_URL}
    model: gpt-x
    params: {temperature: 0, max_tokens: 2048}
    meta: {price_per_1m_input: 0.0, price_per_1m_output: 0.0, deploy: cloud}   # 가격표 값을 넣음
  B:
    type: openai_compat
    base_url: ${LOCAL_URL}
    model: Qwen3.5-27B-FP8
    revision: 1a2b3c4      # 선택. 같은 이름·다른 가중치를 구분(HF 커밋 해시 등)
    params: {temperature: 0, max_tokens: 2048}
    meta: {gpu_cost_per_hour: 0.0, vram_gb: 31, license: Apache-2.0, deploy: on_prem}
    run: {concurrency: 4, timeout_s: 180, max_retries: 2}   # 실행 설정(해시 밖)
prompt: prompts/law_qa_v1.md
judges:
  - {type: rules, role: rules}                                              # 코드 규칙(채점 버전에 들어감)
  - {id: judge1, type: llm, role: primary, base_url: ${JUDGE1_URL}, model: gemma-4-31B-it}   # 주 판정
  - {id: judge2, type: llm, role: secondary, base_url: ${JUDGE2_URL}, model: claude-x}   # 보조 판정(기록만)
questions: datasets/law-v1/dev.jsonl
repeats: 3
level: full   # retrieval_only(검색만) | generation_only(정답 근거 주입) | full(처음부터 끝까지). R0는 generation_only만
run: {invalid_ratio_max: 0.05}   # 실행 무효 상한(해시 밖)
```

### 버전 세 가지와 실행 묶음 해시

| 버전 | 무엇이 들어가나 | 바뀌면 |
| --- | --- | --- |
| 구성 버전(`cfg-`, **arm마다**) | level, level이 쓰는 공통 부품(말뭉치·청킹·검색 …)의 fingerprint, 프롬프트 내용 해시, 그 arm의 생성 모델 fingerprint. arm 이름은 넣지 않는다 | 다른 실험 |
| 채점 버전(`jdg-`) | 코드 규칙 판정의 fingerprint, 주 판정의 fingerprint(모델·revision·디코딩·템플릿·version), 합치는 규칙. 점검 문항·합격선은 U7·R4에서 더한다 | 점수를 서로 비교할 수 없음 |
| 문항 세트 버전(`qs-`) | 문항마다 파싱한 내용(기본값 칸 제외)의 해시를 qid 순으로 정렬해 해시. 파일의 줄 순서·공백·키 순서와 무관 | 다른 시험 |
| 실행 묶음 해시(`run-`) | arm 이름별 구성 버전, 문항 세트 버전, repeats. 채점 버전은 넣지 않는다(한 실행에서 다시 채점할 수 있게) | 이어서 돌 수 없음 |

- **보조 판정**(점수에 쓰지 않는 판정)은 채점 버전에 넣지 않는다. 각자의 fingerprint로 따로 기록한다. 보조 판정을 더하거나 바꿔도 채점 버전은 그대로다. 교차 판정이 점수에 들어가면(R4) 그때 채점 버전에 넣는다.
- **해시 규칙**: YAML 원문이 아니라 부품 fingerprint와 공통 값만 해시한다. 값은 기본값을 채운 뒤의 값(effective value)이고, `None`인 칸만 뺀다. `None`이 아닌 기본값을 가진 칸을 새로 더하거나 기본값·동작을 바꾸면 부품 `version`을 올린다. 정규화 규칙 자체를 바꾸면 해시 규칙 버전(`scheme`)을 올린다. 프레임워크 버전은 기록만 한다.
- **안 쓰는 부품**(예: 생성만 수준의 embedder)은 등록된 이름인지만 확인하고, 만들지도 해시하지도 않는다(경고).
- **원재료**: 해시마다 원재료(정규 JSON으로 만들기 전 값)를 `versions.json`에 함께 남긴다. 실행 기록만으로 해시를 다시 계산해 검증할 수 있다.

**fingerprint에 넣는 것과 빼는 것** (부품이 내놓고, 레지스트리가 `type`·`version`을 붙인다. 판정 부품은 채점 버전으로, 나머지는 구성 버전으로 간다.)

| 넣는다 (바뀌면 다른 실험) | 뺀다 (바뀌어도 같은 실험) |
| --- | --- |
| 등록 이름, 구현 `version` | 서버 주소, API 키·토큰, `${VAR}`, 프록시 사용 여부(`proxy`) |
| 모델 이름·revision·임베딩 차원 | 시간 제한, 재시도, 동시 처리 수 |
| 출력에 영향 주는 파라미터(temperature, max_tokens, seed, k, top_n, 청크 길이, 근거 상한 등) | 모델 meta(가격, GPU 메모리, 라이선스, 폐쇄망 반입, 종료 예정일, deploy) |
| 프롬프트·판정 템플릿 **내용**의 해시 | 절대 로컬 경로(드라이브 문자·`/home/`·`/Users/` 등) |
| 말뭉치 스냅샷의 **내용** 해시(경로가 아님) | |

`check_fingerprint`가 금지 이름과 금지 값을 검사해 멈춘다. 이름은 대소문자·하이픈을 무시하고 중첩까지 본다. 금지 값은 URL, IPv4, 호스트:포트, `${`, 절대 로컬 경로, NaN이다. 끝말·접두어 규칙(`*_key`, `price*` 등)에 걸리는 정상 파라미터는 부품이 `fingerprint_allow`로 선언해 풀 수 있다. 정확한 금지 이름(`api_key`, `base_url`, `meta`, `oc` 등)은 풀 수 없다.

- 비밀값(`${...}`)과 주소는 해시에 넣지 않는다. 같은 모델을 다른 서버에서 돌려도 같은 구성으로 본다. 대신 응답의 실제 모델 이름을 기록해 다르면 경고한다.
- **`${VAR}`는 접속 칸(`base_url`, `api_key`, `oc` …)에만** 쓰고, 접속 칸에는 `${VAR}`만 쓴다. YAML에 주소를 직접 쓰면 값·키·주석·meta 어디든 거부한다(마스킹하지 않음). 주석은 원문 텍스트를 줄 단위로 검사한다. 이 검사를 통과한 치환 전 원문만 `runs/<id>/config.yaml`에 저장한다.
- 값이 하나라도 비어 있거나 알 수 없는 이름이면 실행 전에 멈춘다.

#### 주소·비밀값 검사: 확정 범위와 알려진 남는 위험

검사는 두 겹이다.

1. **첫 번째 겹(프레임워크)**: 구성 YAML 원문(주석 포함)과 부품 fingerprint를 검사한다.
   - 주소: URL, IPv4, 호스트:포트. 문장 속·조사·문장 부호가 붙어도 찾는다.
   - 흔한 비밀값 꼴 7가지: `Bearer`, `sk-`, `hf_`, `ghp_`, `github_pat_`, `AKIA`, `AIza`
   - 접속 칸 리터럴, 절대 로컬 경로
2. **두 번째 겹(저장소)**: gitleaks가 커밋마다 검사한다(pre-commit과 Claude 훅). CI는 전체 이력을 검사한다.

**이 범위는 2026-11-17에 확정했다.** 새 검사 패턴은 **실제로 새는 사례가 나왔을 때만** 더한다. 가설로만 있는 미탐은 아래 목록에 적고 두 번째 겹에 맡긴다. 패턴을 계속 늘리면 오탐이 늘고 규칙이 흔들리기 때문이다.

**알려진 남는 위험**(첫 번째 겹이 잡지 못하는 것):

| 위험 | 예 | 막는 곳 |
| --- | --- | --- |
| 꼴이 정해지지 않은 비밀값이 접속 칸이 아닌 자유 칸이나 주석에 있음 | `# 비번은 hunter2abc`, `params: {note: "x9f…"}` | gitleaks(엔트로피·일반 규칙), 사람 검토 |
| 포트 없는 호스트 이름 | `# 서버 gpu-box에서 돌림` | 주소로 보지 않음. 실제 접속 정보가 아니면 위험이 낮다 |
| 7가지 밖의 업체별 키 꼴 | Slack·Azure 등 | gitleaks 기본 규칙 |
| 프로그램 안에서 `.env`를 여는 경우 | `python -c "open('.env')"` | CLAUDE.md 규칙, 사람 확인(U0) |
| YAML 1.1 bool 변환 | 자유 칸(params)의 `on`/`off` | 스키마가 막는 칸만 안전 |
| 실행 기록 밖의 로그·화면 출력 | 부품이 직접 찍는 로그 | 부품 책임. U6에서 실행 기록 경로를 다시 본다 |
| httpx·httpcore 라이브러리 로거 | INFO 수준에서 요청 주소를 찍는다 | 지금은 로깅 설정이 없어 기본 WARNING이라 새지 않는다. 로깅을 설정하는 U6에서 두 로거를 WARNING으로 묶는다 |
| 응답 모델 이름이 짧은 경로 | `/home/<사용자>`처럼 조각이 둘뿐이면 "마지막 조각"이 사용자 이름이 됨 | 서버가 이런 이름을 낼 일은 드물다. 실제로 나오면 규칙을 고친다 |
| 맨 앞 `/`가 없는 상대 경로 꼴 모델 이름 | 응답 `model`이 `home/u/models/x` | 경로로 보지 않아 경고·served_model에 그대로 남는다. HF 저장소 ID(`org/name`)와 구분할 수 없어서다 |
- 비교 화면은 세 버전 중 무엇이 같고 다른지를 먼저 보여 준다. 채점 버전이 다르면 나란히 놓지 않는다.

### 한 번에 여러 구성 비교

하나씩 바꾼 비교(ablation)를 쉽게 하려고, 기본 구성에 "이 칸만 바꾼" 변형을 여러 개 적는 방식을 지원한다.

```yaml
base: experiments/law_hybrid.yaml
variants:
  vector_only: {retriever: {type: vector, k: 20}}
  top_n_10:   {reranker: {top_n: 10}}
  no_rerank:  {reranker: {type: none}}
```

## 6. 데이터·문항 파이프라인

평가 문항을 만드는 과정 자체를 프레임워크가 지원한다. RAG를 평가하려는 사람은 보통 문항을 어떻게 만들지부터 막히기 때문이다.

### 6.1 말뭉치 수집

- 법령: 국가법령정보센터 Open API(무료 인증키 OC를 환경 변수 `LAW_API_OC`로). 시행일 기준 본문(eflaw)을 받아 스냅샷 폴더에 고정하고, 받은 날짜·기준일·파일별 해시를 기록한다. 법령 본문은 저작권법상 보호받지 않는 저작물이라 예제 스냅샷을 레포에 넣을 수 있다.
- 일반 문서: 폴더를 가리키면 텍스트·마크다운을 읽는다(PDF·HWPX는 나중에).
- 스냅샷은 한 번 만들면 바꾸지 않는다. 새로 받으면 새 스냅샷이다.

### 6.2 문항 만들기

| 단계 | 하는 일 | 누가 |
| --- | --- | --- |
| 1. 초안 | 유형별 템플릿으로 질문·정답 덩어리·must·fail 초안 생성. 어렵게 만들 조건(덩어리가 멀거나, 여러 문서에 걸치거나, 질문에 원문 용어가 없음)을 템플릿에 명시 | LLM(또는 사람이 직접) |
| 2. 기계 검사 | 정답 덩어리가 스냅샷에 있는지, 인용문이 원문과 같은지, 형식이 맞는지 | 코드 |
| 3. 기준 점검 | must·fail이 두 가지 이상으로 읽히는지, 질문에 답이 있는지 | 초안과 다른 LLM |
| 4. 사람 검토 | 대시보드에서 문항마다 채택·수정·버림. 3단계에서 걸린 문항을 앞에 | 사람 |
| 5. 동결 | dev·val·test로 나누고 문항 세트 버전 부여. test는 봉인 | 코드 |

- **분할 규칙**: 정답 덩어리가 세트끼리 겹치지 않게 나눈다. 같은 조문을 묻는 문항이 dev와 test에 나뉘면 test가 사실상 열린 셈이다.
- **쉬운 쪽 쏠림 주의**: LLM이 만든 문항은 쉬운 쪽으로 치우치기 쉽다. 핵심 유형은 사람이 직접 쓰거나, 난이도 조건을 명시해 만들고 사람이 꼭 확인한다.
- **test를 기준선 결과로 고르지 않는다**: "지금 검색이 틀리는 문항"만 모으면 기준선이 낮아 보이는 쏠림이 생긴다. 난이도는 설계 조건으로 만든다.

### 6.3 문항 형식

```json
{"qid": "M001", "type": "multi_article", "split": "dev",
 "question": "...",
 "gold": ["law:000729:제27조", "law:000729:제28조"],
 "must": ["...", "..."], "must_min": 2, "fail": ["..."],
 "optional": ["..."], "scoring_note": "",
 "expected_tool_calls": [], "answer_schema": null,
 "provenance": {"drafted_by": "llm:model-x", "reviewed_by": "human", "checks": ["gold_exists", "quote_match", "ambiguity_ok"]}}
```

provenance에 누가 만들고 누가 검토했는지 남겨, 나중에 "사람이 쓴 문항"과 "LLM이 쓴 문항"의 난이도를 따로 볼 수 있게 한다.

문항 세트 버전은 파일 바이트가 아니라 파싱한 문항(기본값 칸 제외)으로 계산한다(§5 표). provenance가 바뀌면 다른 세트다.

## 7. 실행·채점·게이트

### 7.1 실행

- 문항 × 구성(A·B·…) × 반복 횟수만큼 항목을 만들어 돌린다. 동시 처리 수는 구성마다 정한다.
- 항목마다 검색 후보(순위·점수), 리랭크 결과, 모델에 넘긴 근거, 답, 토큰·지연·finish\_reason을 기록한다.
- 실패는 셋으로 나눈다(§4 "실패 분류 셋").
  - **서버 사정**(연결·시간 초과·408·429·5xx·모르는 오류): 클라이언트가 호출 안에서 재시도하고, 그래도 실패한 항목은 실행이 끝난 뒤 한 번 다시 돌린다. 남은 비율이 상한을 넘으면 실행 무효로 표시한다(불합격과 구분).
  - **모델·문항 사정**(그 밖의 4xx·응답 형식 오류·잘림): 다시 돌리지 않고 항목 실패로 채점한다. 건수는 따로 표시한다.
  - **설정 오류**(401·403·404): 실행을 바로 멈춘다.
- 중간에 끊기면 이어서 돌 수 있다. 끝난 항목은 다시 부르지 않는다.

### 7.2 채점 순서

1. **코드 규칙**: 인용 재현율·정밀도, 도구 호출 정답, JSON 칸 정답, 거절 여부, 검색 지표(recall@k, 문항 단위 '정답 모두 근거 안').
2. **LLM 판정**: must·fail 항목별 참·거짓만 내고, 정오는 코드가 계산한다. 구성 이름은 판정에 보이지 않는다. 처음과 끝에 점검 문항을 다시 채점해 기준선과 다르면 멈춘다. 잘린 판정은 믿지 않는다.
3. **교차 판정**: 판정 모델이 둘 이상이면 합치는 규칙(둘 다 같으면 채택, 어긋나면 사람 대기열)을 구성에 적는다.
4. **사람 채점**: 표본(유형별 층화)과 교차 판정에서 어긋난 답을 블라인드로. 일치율(정오·must 항목)과 κ를 자동으로 낸다.

### 7.3 게이트

P0의 절차를 프레임워크가 강제한다. 사용자는 "실험 모드"와 "검증 모드" 중 고른다.

| 모드 | 언제 | 제약 |
| --- | --- | --- |
| 실험 | 구성을 이것저것 바꿔 볼 때 | dev만 사용 가능 |
| 검증 | 결론을 내야 할 때 | 아래 순서를 따라야 test가 열림 |

검증 모드 순서:

1. dev로 구성 조정(여러 번 가능)
2. 조합이 정해지면 val을 **한 번** 돌려 동결값의 근거로
3. 합격선을 정해 **동결**: 합격선이 채점 버전에 들어가고, 기준표의 조건과 코드 조건 목록을 자동 대조
4. test를 **한 번**: 동결 기록이 있고 구성·채점 버전이 동결과 같을 때만 열림
5. 코드가 합격 판정(실행 무효 > 불합격 > 판정 보류 > 합격). **판정 보류**는 판정 불가 항목(잘린 판정, 점검 문항 이탈)이나 사람 채점 대기 항목이 남아 합격 여부를 확정할 수 없는 상태다.

- 같은 test를 두 번 열면 기록에 남고 보고서에 표시된다.
- 동결 기록은 git 태그 대신 프레임워크 저장소에 남긴다(git 없이도 동작). git 태그 연동은 선택.

### 7.4 모델 선택 지표

"어떤 모델을 쓸까"는 품질만으로 정할 수 없다. 구성마다 아래를 한 표로 낸다.

| 기준 | 계산 |
| --- | --- |
| 품질 | 유형별 정답률, 인용 재현율·정밀도, 거절 정확도, 기준 모델 대비 비율 |
| **비용** | 문항 1,000개당 비용. 상용은 실제 입력·출력 토큰 × 단가, 로컬은 실행 시간 × GPU 시간당 비용 |
| 속도 | p50·p95 지연(측정 조건을 함께 표시) |
| 설치 조건 | 필요한 GPU 메모리, 라이선스, 폐쇄망 반입 가능 여부 |
| 수명 | 상용 모델 종료 예정일, 응답의 실제 모델 이름이 설정과 다르면 경고 |

- 품질 비교는 **생성만(정답 근거 주입)** 수준에서 하는 것을 기본으로 한다. 검색이 모델 비교에 섞이면, P0처럼 모델과 관계없이 A·B가 함께 떨어져 차이가 가려진다.
- 가격은 바뀌므로 비용은 토큰·시간 기록에서 화면을 볼 때 다시 계산한다. 실행 기록에는 토큰·시간만 남긴다.

### 7.5 실패 위치 진단

"부족한 곳을 찾기"를 프레임워크가 자동으로 한다. 틀린 항목마다 정답이 어디서 빠졌는지 나눈다. P0에서 사람이 손으로 한 진단(원인 분석·R2)을 기본 기능으로 만든 것이다.

| 위치 | 뜻 | 고칠 부품 |
| --- | --- | --- |
| 청킹 | 정답 내용이 덩어리 경계에서 잘렸거나 여러 덩어리로 흩어짐 | Chunker |
| 검색 후보 밖 | 정답 덩어리가 검색 후보(상위 k)에 없음 | Embedder, Retriever(키워드 추가 등) |
| 리랭크가 밀어냄 | 후보에는 있었는데 근거(상위 n) 밖으로 밀림 | Reranker, 근거 개수 |
| 근거 상한 | 글자 상한 때문에 잘려 나감 | 근거 글자 상한 |
| 생성 | 정답이 근거에 다 있는데 답이 틀림 | Generator, 프롬프트 |
| 잘림·형식 | 출력 상한 초과, JSON 형식 오류 | Generator 설정 |

- 항목 단위와 문항 단위(여러 회 반복 중 하나라도 빠지면 빠짐)로 둘 다 집계한다.
- 핵심 지표는 문항 단위 \*\*'정답 덩어리가 근거에 모두 든 비율'\*\*이다. 근거가 모두 든 문항과 빠진 문항의 정답률을 따로 내면 검색 탓인지 생성 탓인지가 바로 갈린다(P0: 모두 든 문항 B 75%·A 79%, 빠진 문항 A·B 0%).
- recall@k는 리랭크 앞 후보 기준과 리랭크 뒤 근거 기준을 구분해 표시한다. P0에서는 이 둘이 섞여 해석이 늦어졌다.

## 8. 저장 구조와 대시보드 화면

### 8.1 저장

실행 기록의 정본은 **파일**이고, SQLite는 화면과 검색을 위한 색인이다. SQLite가 사라져도 파일에서 다시 만들 수 있다(P0의 restore-check와 같은 생각).

```text
workspace/
├─ snapshots/<corpus>/          # 말뭉치 스냅샷 + manifest(해시)
├─ datasets/<name>/            # 문항: draft/ reviewed/ frozen/{dev,val,test}.jsonl + manifest
├─ indexes/<해시>/             # 청킹·임베딩 결과 캐시(같은 구성이면 다시 안 만듦)
├─ runs/<run_id>/
│  ├─ config.yaml · versions.json   # 치환 전 원문 · 버전 해시와 원재료·보조 판정 기록
│  ├─ items.jsonl              # 항목별 검색·답·지연
│  ├─ judgments/<채점 버전>.jsonl
│  ├─ human/<표본>.jsonl          # 사람 채점
│  └─ report.json · report.md
├─ gates/                      # 동결 기록, test 열람 기록
└─ index.sqlite                # 화면용 색인(파일에서 다시 만들 수 있음)
```

- 임베딩 결과는 구성 해시로 캐시해, 검색 전략만 바꾼 비교에서 다시 임베딩하지 않는다.
- 비밀값과 서버 주소는 어떤 파일에도 저장하지 않는다.

### 8.2 대시보드 화면

| 화면 | 내용 |
| --- | --- |
| **실험 만들기** | 부품별로 등록된 구현을 고르고 설정을 채움(설정 폼은 부품의 Pydantic 스키마에서 자동 생성). 기준 구성에서 칸 하나씩 바꾼 변형 추가, 문항 세트·평가 수준(검색만·생성만·끝까지)·반복 횟수 선택, 실행 전 설정 검사와 예상 비용·호출 수 표시, YAML 미리보기·저장, 실행 시작. 검증 모드에서는 게이트 조건(동결 등)을 만족해야 test를 고를 수 있음 |
| **실행 현황** | 진행률(항목 수), 실패·재시도, 중단·이어서 돌기, 끝나면 채점·보고서로 바로 이동 |
| 문항 검토 | 초안을 하나씩 보고 채택·수정·버림. 원문을 옆에 띄워 정답 덩어리를 바로 확인, 기준 점검에서 걸린 문항을 앞에 |
| **모델 선택** | 생성 모델 후보를 품질·비용(문항 1,000개당)·속도·설치 조건·수명으로 한 표에. 품질과 비용을 두 축으로 놓은 그림, 폐쇄망 가능 모델만 걸러 보기 |
| 실험 목록 | 실행마다 구성·문항 세트·채점 버전, 평가 수준, 상태, 핵심 지표. 같은 조건끼리 묶음. 어떤 실행이든 구성을 불러와 고쳐 다시 돌리기 |
| 비교 | 두 실행(또는 변형 여러 개)을 유형별·지표별로 나란히, 문항별 얻음·잃음 목록, 구성 차이(바뀐 칸만), **실패 위치 분포**(검색 후보 밖·리랭크·생성 등)가 어떻게 바뀌었는지 |
| 문항 상세 | 질문, 검색 후보와 순위, 리랭크 결과, 정답 덩어리가 어디서 빠졌는지(실패 위치), 답, 판정 결과 |
| **답 채점** | 블라인드(구성 이름·판정 결과 가림), must·fail 항목별 버튼, 단축키, 자동 저장, 교차 판정에서 어긋난 답만 모아 보기, 끝나면 일치율·κ |
| 게이트 | dev·val·test 상태, 동결 여부, 기준표와 코드 조건 대조 결과, 합격 판정 |

**화면에서 실행하는 구조**: 실험은 시간이 오래 걸려 백엔드가 작업 대기열에 넣고 별도 작업 프로세스가 돌린다. 화면은 진행 상황을 읽기만 하므로 브라우저를 닫아도 실행은 계속된다. 화면에서 시작한 실행과 CLI로 시작한 실행은 같은 실행 기록을 남긴다. API 키 같은 비밀값은 화면에서 입력받지 않고 서버의 환경 변수 이름만 고른다.

**블라인드는 서버가 지킨다.** 채점 화면에 보내는 데이터에는 처음부터 구성 이름·판정 결과·문항 ID가 없고(임의 표본 ID만), 대조표(key)는 서버에만 있다. 화면 코드를 열어도 정답이 보이지 않게 하려는 것이다. P0 채점 페이지(sample.json / key.json 분리)와 같은 원칙이다.

## 9. 레포 구조와 기술 스택

### 9.1 기술 스택

| 층 | 선택 | 이유 |
| --- | --- | --- |
| 언어·패키지 | Python 3.12 이상(CI 3.12·3.14), uv | RAG 생태계, P0와 같은 도구 |
| 모델 호출 | OpenAI 호환 SDK(httpx) | vLLM·Ollama·상용 API를 주소만 바꿔 사용 |
| 설정 검증 | Pydantic | 빈 값·잘못된 값을 실행 전에 걸러냄 |
| CLI | Typer | `ragexp run`, `ragexp judge`, `ragexp report` 같은 명령 |
| 저장 | 파일(JSONL) + SQLite 색인 | 설치 없이 동작, 다시 계산 가능 |
| 백엔드 | FastAPI | 대시보드 API, 블라인드 채점 서버 |
| 화면 | React + Vite + TypeScript | 단축키·저장이 중요한 검토 화면 |
| 시험 | pytest, 가짜 모델 서버 | GPU·네트워크 없이 전부 도는 시험 |
| 라이선스 | Apache-2.0(저작권자 석한나) | 특허 조항 포함, 기업에서 쓰기 편함 |

### 9.2 레포 구조 (설계안)

```text
rag-experiment-framework/
├─ src/ragexp/
│  ├─ components/      # corpus, chunker, embedder, vector_store, retriever, reranker, generator, judge
│  ├─ types.py         # 도메인 타입(pydantic, 불변)
│  ├─ fingerprint.py   # fingerprint 검사(주소·비밀값·meta·경로 금지)
│  ├─ registry.py      # 부품 등록·생성, entry point
│  ├─ config.py        # YAML → Pydantic, 변형 펼치기
│  ├─ versioning.py    # 구성·채점·문항 세트 해시
│  ├─ client.py        # 모델 호출 통로(재시도·기록·잘림)
│  ├─ runner.py        # 실행·이어서 돌기
│  ├─ metrics.py       # 검색·인용·정답률 지표
│  ├─ judging.py       # 코드 규칙·LLM 판정·교차 합치기·점검 문항
│  ├─ human.py         # 표본 뽑기·블라인드·일치율
│  ├─ gates.py         # dev/val/test, 동결, 합격 판정
│  ├─ datasets/        # 말뭉치 수집, 문항 생성·검사·분할
│  ├─ store.py         # 파일 저장·SQLite 색인
│  ├─ api/             # FastAPI
│  └─ cli.py
├─ web/                 # React 대시보드
├─ examples/law_ko/     # 법령 예제: 구성 YAML, 프롬프트, 문항 일부
├─ tests/
└─ docs/                # 설계·사용법·부품 만들기
```

**예제의 기준선 구성**: `examples/law_ko`에는 DASP P0의 검색과 같은 구성을 기준선으로 둔다. 조 단위 청킹, KURE-v1 임베딩, 정확 벡터 검색 상위 20개, 조문 번호 정확 일치, 리랭커 상위 5개, 근거 7,800자 이내다. 새 검색 전략(하이브리드 등)은 이 기준선에서 한 칸씩 바꾼 변형으로 비교한다. 코드는 새로 짜고 설정값만 똑같이 맞춘다.

### 9.3 개발 방식

- Claude Code로 개발하고, DASP와 같은 단위·블록 방식(설계 → 구현 → 시험 → 보고 → 커밋)을 따른다.
- 공개 레포라 커밋 전마다 gitleaks로 비밀값을 검사하고, 예제에는 실제 서버 주소를 넣지 않는다.
- DASP 레포의 코드는 옮기지 않는다. 원칙과 경험만 가져온다.

## 10. 로드맵과 완료 기준

| 단계 | 할 일 | 완료 기준 |
| --- | --- | --- |
| **R0 최소판: "어떤 모델을 쓸까"** | 부품 인터페이스·등록, 구성 YAML·해시, 모델 호출 통로, 실행·기록, 코드 규칙·LLM 판정, 보고서, 법령 말뭉치 수집, **생성만(정답 근거 주입) 모드, 비용 지표, 여러 생성 모델 한 번에 비교** | 법령 예제(조문 수십 개·문항 20개)로 생성 모델 3개 이상을 생성만 수준에서 비교해 품질·비용·속도 표가 나오고, 같은 구성을 다시 돌리면 같은 구성 버전, 시험이 GPU 없이 전부 통과 |
| **R1 대시보드** | **실험 만들기(부품 선택·조합·변형)·실행 현황(작업 대기열)**, 모델 선택·실험 목록·비교·문항 상세, 블라인드 답 채점, 일치율 | 화면만으로 부품을 골라 구성을 만들고 실행·비교·채점까지 끝낼 수 있고, 화면에서 만든 구성을 CLI로 다시 돌리면 같은 구성 버전. 채점 화면 데이터에 구성 이름·판정 결과가 없음(시험으로 확인) |
| **R2 검색 부품: "어디가 부족한가"** | 번호 정확 일치·BM25·하이브리드, 리랭커 교체, 청킹 전략, pgvector 등 벡터DB, 검색만 평가, 변형 비교, 임베딩 캐시, **실패 위치 진단**, P0 기준선 예제 | P0 기준선에서 검색 전략만 바꾼 변형 3개를 생성 없이 비교하고, 문항 단위 '정답 모두 근거 안' 비율과 실패 위치 분포를 보여 줌 |
| **R3 문항 파이프라인** | LLM 초안, 기계 검사, 기준 점검, 문항 검토 화면, 분할·동결 | 법령으로 문항 세트를 만들어 dev·val·test로 얼리고, 정답 덩어리가 세트끼리 겹치지 않음을 검사로 확인 |
| **R4 게이트·생성** | 검증 모드(동결·봉인·합격 판정·기준표 대조), 교차 판정, 생성 전략(프롬프트) 비교, 게이트 화면 | 동결 없이 test가 열리지 않고, 합격 판정이 코드로 나옴 |

R0는 1\~2주, 이후 단계는 R0를 마친 뒤 다시 잡는다. 문항 파이프라인(R3)을 검색 부품(R2) 뒤에 둔 것은, 처음에는 사람이 쓴 작은 문항 세트로도 나머지를 검증할 수 있기 때문이다.

### DASP와의 관계

DASP P1-1(법령 검색 개선)은 지금 DASP 하네스로 진행하고, 프레임워크는 나란히 만든다. R2가 끝나면 P1-1 검색 비교 결과를 프레임워크로 재현해 검증하고, 재현이 맞으면 그때부터 프레임워크로 옮긴다.
